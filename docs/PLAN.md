# Свой плагин «Ozon Доставка для WooCommerce» — аналитика и план

Дата: 26.08.2026. Редакция 2: переписана по реальной спецификации `docs.ozon.ru/api/ozon-delivery/swagger.json` (OpenAPI 3.0.4, 171 КБ, 18 методов), прочитанной через браузер.

**Первая редакция была построена на догадках про Seller API и оказалась неверной по трём ключевым пунктам.** Что изменилось: это отдельный API на своём хосте, авторизация OAuth, привязки к карточкам товаров на Ozon нет, стоимость доставки API отдаёт.

## 0. Спецификация: где брать

```
https://docs.ozon.ru/api/ozon-delivery/swagger.json
```

Файл существует и отдаётся публично (именно его грузит сама страница документации). 171 КБ, OpenAPI 3.0.4, 18 путей. Из моей песочницы домен закрыт, но у Claude Code на твоей машине доступ обычный:

```bash
mkdir -p docs && curl -sS https://docs.ozon.ru/api/ozon-delivery/swagger.json -o docs/ozon-delivery.swagger.json
```

171 КБ целиком в контекст класть не надо. Один раз сгенерировать из него `docs/API.md` (таблица методов + деревья полей, как в разделе 3 ниже) и дальше работать с ним, а в swagger заглядывать точечно через `jq` за конкретной схемой.

Важное про текстовые разделы: описания `Introduction`, `GetStarted`, `Process`, `Status Model`, `Error Codes` лежат не на страницах, а внутри того же swagger, в `tags[].description` в формате Markdown. То есть **вся документация целиком — это один файл**, ходить по страницам не нужно вообще.

## 1. Что это на самом деле за API

### Отдельный продукт, не Seller API

| Параметр | Значение |
|---|---|
| Хост API | `https://api-delivery.ozon.ru` |
| Авторизация | OAuth 2.0, `client_credentials` |
| Точка выдачи токена | `POST https://xapi.ozon.ru/oauth/token` |
| Параметры | `client_id`, `client_secret`, `grant_type=client_credentials`, `scope` |
| Заголовок запросов | `Authorization: Bearer <access_token>` |
| Идемпотентность | заголовок `Idempotency-Key` (UUID) на создании заказа |

Ключи создаются в личном кабинете **Ozon Доставки**: Настройки → Управление частными приложениями → Создать. Там же выдаются scope:

- `delivery-api.delivery` — проверка доступности и сроков;
- `delivery-api.delivery-point` — пункты выдачи;
- `delivery-api.order` — оформление заказа;
- `delivery-api.posting` — отправления;
- `delivery-api.return` — возвраты;
- `delivery-api.all` — всё сразу.

Можно выдать доступ к частному приложению разработчику отдельно от владельца кабинета. Для тебя это значит: доступ мне или подрядчику даётся без передачи логина от кабинета.

### Главная поправка к первой редакции

**Привязки к карточкам товаров на Ozon нет.** В `POST /v1/order/create` отправление описывается так:

```
postings[].description        — свободный текст, что внутри
postings[].declared_value     — объявленная стоимость (amount строкой + currency_code)
postings[].dimensions         — weight_g, length_mm, width_mm, height_mm
postings[].shipment_method_id — метод доставки из кабинета
```

Ни SKU, ни offer_id, ни артикула Ozon. То есть гипотеза «товар должен быть представлен и на Ozon» к этому API не относится — она из маркетинговых материалов про другую схему. Требования к самому аккаунту всё равно надо уточнить, но техническая связка с маркетплейсом отсутствует.

**Для магазина 18+ это меняет картину в лучшую сторону:** что увидит покупатель и логистика, определяешь ты сам строкой `description`. Название девайса туда класть не обязано.

### Методы (все 18)

| Метод | Назначение |
|---|---|
| `POST /v1/delivery/check-client` | `phone_number` → `can_be_delivered` (bool) |
| `POST /v1/delivery/location` | предварительный срок по координатам покупателя, до выбора товара |
| `POST /v1/order/checkout` | расчёт: стоимость доставки, стоимость страховки, срок, cutoff |
| `POST /v1/order/create` | создание заказа с одним или несколькими отправлениями |
| `POST /v1/delivery-point/list` | список ПВЗ, курсорная пагинация, **только id + shipment_method_ids** |
| `POST /v1/delivery-point/info` | полные данные точек по массиву id |
| `POST /v1/delivery-point/check-availability` | подойдут ли конкретные точки под ОВХ и стоимость заказа |
| `POST /v1/posting/approve` | подтвердить отправление к отгрузке |
| `POST /v1/posting/label` | этикетка (обязательна для приёмки) |
| `POST /v1/posting/search` | поиск отправлений с фильтрами и пагинацией |
| `POST /v1/posting/info` | параметры и статус отправления |
| `POST /v1/posting/status-history` | история статусов |
| `POST /v1/posting/cancel` | запуск отмены |
| `POST /v1/return/search` | список отмен и возвратов |
| `POST /v1/return/info` | параметры возврата |
| `POST /v1/return/status-history` | история статусов возврата |
| `POST /v1/return/download_barcode` | PDF со штрихкодом получения возвратов |
| `POST /v1/return/reset_barcode` | сброс штрихкода |

Всё POST, всё JSON. Ни одного GET.

### Ключевые схемы

**`/v1/order/checkout` (запрос):**
```
recipient.phone_number*
postings[]: request_id*, shipment_method_id*, cutoff_at,
            declared_value{amount*, currency_code*},
            dimensions{weight_g*, length_mm*, width_mm*, height_mm*}
delivery.delivery_point.delivery_point_id   ИЛИ
delivery.courier.coordinates{latitude*, longitude*}
```

**`/v1/order/checkout` (ответ):**
```
results[]: request_id, posting{ estimated_delivery_cost{amount,currency_code},
                                estimated_insurance_cost{...},
                                estimated_delivery_days, cutoff_at },
           error{code, message}
```

Стоимость API отдаёт. Утверждение ApiShip, что Ozon Доставка цену не возвращает, к этому API не относится.

**`/v1/order/create` (запрос)** — то же плюс `order_external_id`, `recipient.full_name`, `postings[].description*`, `postings[].posting_external_id`, а для курьера полный адрес: `zip_code*, country*, region*, city*, street*, house_number, entrance, floor, apartment, intercom`.

**`/v1/order/create` (ответ):** `order_number`, массив `postings[]` с `posting_number` и предварительной стоимостью по каждому.

**`/v1/delivery-point/info` (ответ по точке):** `name`, `delivery_point_number`, `type`, `full_address`, `coordinates`, `schedule[]` (дата + периоды работы), `is_active`, `storage_period_days`, `fitting_rooms_count`, `is_bulky`, `restrictions{min/max_weight_g, max_width/length/height_mm, min_price, max_price}`.

**Модель статусов отправления:** `CREATED`, `FORMING`, `FORMING_FAILED`, `READY_FOR_SHIPPING`, `ON_WAY`, `IN_DELIVERY_POINT`, `IN_COURIER_SERVICE`, `DELIVERED`, `CANCELED`, плюс отдельные модели для возвратов (`MOVING`, `AT_THE_PICK_UP_POINT`, `RECEIVED`, `UTILIZATION`, `UTILIZED`, `WRITTEN_OFF`, `LOOKING_FOR`) и для грузомест (`FORMED`, `ACCEPTED`, `DRIVER_PICK_UP`, `FINISHED`).

**Коды ошибок** (примеры): `DPRE` точка не подходит под параметры заказа, `SDPE`/`SPE` точка доставки совпадает с точкой отгрузки, `DPNF` нет информации о точке, `DAE` не удалось рассчитать доставку до точки, `DCE` ошибка предрасчёта стоимости или страховки, `RE` невозможно доставить получателю, `PE` кабинет продавца заблокирован, `OE` общая ошибка расчёта. Ошибки приходят **внутри 200-го ответа**, per-posting, в поле `error` — это принципиально для обработки: HTTP 200 не означает успех.

### Порядок работы, как его описывает сам Ozon

**Подготовка в кабинете (без API).** В разделе «Методы доставки» создаётся метод: как и куда ты передаёшь отправления. Методов может быть несколько с разными точками отгрузки. Каждому генерируется штрихкод с номером, который и есть `shipment_method_id`. Каждое отправление в заказе привязывается к одному из методов.

**Оформление:**
1. Покупатель авторизуется на сайте продавца.
2. `check-client` по телефону. Доставка доступна только зарегистрированным на Ozon.
3. `delivery/location` — примерный срок по координатам, пока товар не выбран.
4. Покупатель выбирает тип доставки: ПВЗ или курьер.
5. Для ПВЗ: `delivery-point/list` (весь каталог), фильтрация и отрисовка **на своей стороне**, `check-availability` под конкретный заказ, `delivery-point/info` для адреса и графика.
6. `order/checkout` — проверка возможности и предрасчёт.
7. Покупатель оформляет заказ.
8. `order/create`. Перед ним рекомендуется повторить `checkout` с теми же параметрами, чтобы убедиться в актуальности расчёта.

**Отгрузка:**
1. `posting/approve` — подтверждение начала сборки.
2. Ozon проверяет **баланс продавца**. Без денег на балансе отгружать нельзя.
3. `posting/info` — результат подтверждения. При успехе статус `READY_FOR_SHIPPING`.
4. `posting/label` — этикетка, только в статусе `READY_FOR_SHIPPING`, обязательна для приёмки.

**Обработка и отмены:** `posting/search`, `posting/info`, `posting/status-history`. Отмена через `posting/cancel`, доступна до определённого статуса, результат проверяется отдельно, движение отменённого отправления обратно отслеживается методами возвратов.

### Отдельно: защита от DDoS

Это самый неприятный технический пункт, и он спрятан в разделе GetStarted.

Серверы API закрыты модулем `testcookie`. Ожидаемое поведение клиента:

1. Модуль перехватывает входящий запрос для проверки.
2. Сервер отвечает редиректом **302 или 307** с заголовками `Location` и `Set-Cookie`.
3. Клиент повторяет запрос **с тем же телом** по адресу из `Location`, приложив полученный `Cookie`.
4. Клиент сохраняет cookie и использует его в последующих запросах.
5. Дальше запросы идут без редиректов, пока cookie валиден. Значение уникально, зашифровано и **может измениться без уведомления**.

В примере из документации это решается через `curl -sL` с cookie jar (`.b2c_cookies`). В WordPress так просто не выйдет, и вот почему это важно спроектировать сразу:

- `wp_remote_post()` при редиректе через cURL-транспорт по умолчанию **превращает POST в GET на 302** и теряет тело. Нужен либо ручной цикл редиректов (`redirection => 0`, разбор `Location` и `Set-Cookie`, повтор POST руками), либо `CURLOPT_POSTREDIR` через `http_api_curl`.
- Cookie надо хранить между запросами (транзиент или опция) и уметь сбрасывать при 302 в неожиданном месте.
- На это же надо писать тест: половина будущих багов «на чужом хостинге не работает» будет отсюда, потому что поведение зависит от транспорта (cURL или PHP streams).

Это ровно тот класс проблем, из-за которого готовые плагины потом обрастают заплатками. Решается один раз, в слое транспорта, и закрывается тестом.

## 2. Что уточнить у Ozon до кода

Список сократился, но не исчез.

1. **Категория 18+.** Товары для взрослых в перечне запрещённых к перевозке Ozon Доставкой — проверить письменно. Это блокер всей затеи, снимать первым.
2. **Требования к аккаунту.** Нужен ли действующий селлерский аккаунт с продажами, или достаточно кабинета Ozon Доставки. По API привязки нет, но доступ к кабинету регулируется отдельно.
3. **Тестовый контур.** В спеке один сервер, `api-delivery.ozon.ru`, песочницы не заявлено. Если её нет — все тесты создают реальные отправления, и нужен режим dry-run внутри плагина плюс аккуратный ручной прогон.
4. **Лимиты.** В спеке есть ответ `429` у всех методов, но конкретных цифр нет. Спросить RPS и дневные квоты, особенно по `delivery-point/list` и `posting/search`.
5. **Как часто меняется каталог ПВЗ** и есть ли инкрементальная выгрузка. Сейчас видно только курсорный полный обход.
6. **Вебхуки.** В спеке их нет вообще, статусы только опросом. Уточнить, планируются ли пуши.

## 3. Архитектура плагина

### База

- PHP 8.1+, WordPress 6.4+, WooCommerce 8.2+, проверка версий при активации.
- Composer + PSR-4, зависимости через php-scoper.
- HTTP только через `wp_remote_*`, но с собственным слоем редиректов и cookie (см. выше).
- HPOS: объявить совместимость с `custom_order_tables`.

### Что здесь неочевидно и определяет объём работ

**Карту ПВЗ ты рисуешь сам, готового виджета нет.** `delivery-point/list` возвращает только `delivery_point_id` и `shipment_method_ids` с курсорной пагинацией; адреса и координаты добираются через `delivery-point/info` пачками. Значит нужна:

- своя таблица `wp_ozon_delivery_points` с координатами, адресом, графиком, ограничениями и активностью;
- фоновая синхронизация каталога (Action Scheduler, чанки по курсору, устойчивость к обрыву);
- геопоиск на своей стороне: город или bbox → выборка точек;
- предварительная фильтрация по `restrictions` (вес, габариты, min/max объявленной стоимости) **до** обращения к `check-availability`, иначе будешь дёргать API впустую;
- карта на фронте: Яндекс.Карты или Leaflet поверх своей ручки AJAX.

Это плюс, а не минус: именно из-за чужой «публичной витрины» с Яндексом были пустые карты в Когалыме. Здесь источник один и он твой.

**Габариты обязательны в каждом запросе.** `weight_g`, `length_mm`, `width_mm`, `height_mm` — обязательные поля и в `checkout`, и в `create`, и в `check-availability`. Значит: настройки габаритов по умолчанию, конвертация из единиц WooCommerce, и алгоритм упаковки корзины в одно или несколько отправлений. Простой вариант для v1: одно отправление на заказ, сумма весов, габариты по максимуму плюс запас, всё через фильтр.

**`declared_value` — отдельное решение.** Объявленная стоимость влияет на страховку, на её цену и на доступность точек (`min_price`/`max_price` в restrictions). Настройка «процент от суммы заказа» и фильтр.

**`request_id` и `posting_external_id`.** В `checkout` и `create` каждое отправление помечается `request_id` (целое, твоя нумерация в рамках запроса) — по нему приходят и результаты, и ошибки. `posting_external_id` и `order_external_id` — твои идентификаторы, туда кладём номер заказа WooCommerce. Это же основа идемпотентности вместе с `Idempotency-Key`.

**Ошибки внутри 200.** Обработчик обязан разбирать `results[].error.code` и маппить `DPRE`, `DAE`, `RE`, `DCE`, `PE` в понятные покупателю и админу сообщения. И не через `wc_add_notice(..., 'error')` на этапе расчёта корзины: это ловит `check_cart_items()` и валит весь чекаут. Своя строка в таблице заказа плюс флаг в сессии.

**Баланс кабинета.** `approve` упирается в баланс. Health check в админке должен показывать это до того, как заказы встанут.

## 3.1 Тесты: обязательный режим работы

Разработка ведётся тестами вперёд. Правило простое: **ни одна функция бизнес-логики не пишется, пока на неё нет падающего теста.**

Цикл на каждую задачу:

1. Тест на ожидаемое поведение. Запустить, убедиться, что он **красный** по нужной причине, а не из-за опечатки.
2. Минимальный код, который делает его зелёным.
3. Рефакторинг при зелёных тестах.
4. Коммит. Код без теста в коммит не уходит.

### Что покрывается обязательно

| Слой | Чем проверяется |
|---|---|
| `Api\Transport` | мок `pre_http_request`: 307 с `Location` и `Set-Cookie` → повтор POST **с тем же телом** и cookie → 200. Отдельно: 302, смена cookie в середине сессии, зацикленный редирект, таймаут |
| `Api\TokenStore` | получение токена, кэш, обновление до истечения, реакция на 401 |
| Ретраи и 429 | экспоненциальная пауза, лимит попыток, отсутствие ретрая на неидемпотентных вызовах |
| `Shipping\Dimensions` | все единицы WooCommerce → граммы и миллиметры, округление, пустые значения → дефолты |
| Упаковка отправлений | корзина → `postings[]`, суммы весов, `request_id`, объявленная стоимость |
| Разбор ответов | `results[].error` внутри 200: каждый код (`DPRE`, `DAE`, `DCE`, `RE`, `PE`, `SDPE`, `DPNF`, `OE`, `NEB`, `PNF`) → своё сообщение и своё поведение |
| Деньги | `{amount: string}` → без float, сравнение и суммирование строками или в копейках |
| Идемпотентность | повтор `order/create` с тем же ключом не создаёт второе отправление |
| Маппинг статусов | все 9 статусов отправления и 7 возврата → статусы заказа WooCommerce |
| `Points\Repository` | фильтр по `restrictions` (вес, габариты, min/max стоимости), геовыборка |
| Чекаут | `check-client` отвечает `false` → метод доставки исчезает корректно, чекаут не ломается |
| Фоновые задачи | обрыв синхронизации каталога на середине курсора → продолжение с того же места |

Сквозной чекаут (`товар → корзина → выбор ПВЗ → оформление`) — Playwright, один сценарий на ПВЗ, один на курьера.

### Где TDD в чистом виде не работает

Транспорт и схемы ответов Ozon тестируются на **фикстурах**, а фикстуры берутся из живых ответов. Порядок здесь обратный: один раз руками дёрнуть метод, записать ответ в `tests/Fixtures/`, дальше уже писать тесты и код против фикстуры. Придумывать структуру ответа самому нельзя — это единственное исключение из «тест первым».

Соответственно нужна CLI-команда записи фикстур: `wp ozon raw /v1/posting/info --json=… --save-fixture=posting-info-delivered`.

### Порог

CI роняет сборку, если: упал хоть один тест, PHPStan ниже 6 уровня, PHPCS ругается, покрытие `src/Api` и `src/Shipping` ниже 80%. Остальные слои без порога, но без тестов туда всё равно не коммитим.

## 4. Фазы

**0. Каркас.** Репозиторий, bootstrap, guards, настройки (client_id, client_secret, scope), логгер. На фронт ничего не влияет.

**1. Транспорт и авторизация.** OAuth с кэшем токена, обработка `testcookie` (302/307 + cookie), ретраи, 429. Кнопка «Проверить подключение» и страница диагностики. **Это самая рискованная часть, поэтому она вторая, а не пятая.**

**2. Каталог ПВЗ.** Синхронизация в свою таблицу, экран в админке (сколько точек, когда обновлялись), геовыборка.

**3. Метод доставки до ПВЗ.** Расчёт через `order/checkout`, выбор точки на чекауте (сначала список с поиском по городу, карта следом), `check-client` по телефону, `check-availability`, валидация, сохранение точки в мету заказа. Заказ в Ozon пока не уходит.

**4. Передача заказа.** `order/create` кнопкой, потом автоматически. Идемпотентность, разбор per-posting ошибок, мета с `order_number` и `posting_number`.

**5. Отгрузка и статусы.** `approve`, `label` (PDF в админке), `posting/info` и `status-history` по расписанию, отражение в заказе и письмах.

**6. Отмены и возвраты.** `posting/cancel` с проверкой результата, `return/*`, штрихкод получения возвратов.

**7. Курьер, карта, блочный чекаут, i18n, документация.**

До первого боевого заказа нужны фазы 0–5.

## 5. Отладка

- **wp-env** (docker) для локального WordPress с WooCommerce. Поднимается и сбрасывается одной командой, Claude Code работает с этим из терминала.
- **WP_DEBUG / WP_DEBUG_LOG / SCRIPT_DEBUG** и отключённый fatal error handler.
- **Query Monitor** — видно каждый HTTP-запрос плагина, время и ответ.
- **WooCommerce → Статус → Журналы**, источник `ozon-delivery`, ключи и токены маскируются.
- **Свои WP-CLI команды:** `wp ozon token`, `wp ozon points sync`, `wp ozon checkout <order_id>`, `wp ozon push <order_id>`, `wp ozon raw /v1/posting/info --json=…`. Экономит десятки прогонов чекаута руками.
- **Фикстуры + мок транспорта** через фильтр `pre_http_request`: записанные ответы Ozon в `tests/Fixtures`, дальше юниты гоняются офлайн.
- **Отдельный тест на редиректы `testcookie`:** мок, который на первый POST отвечает 307 с `Location` и `Set-Cookie`, а на повтор с cookie — 200. Если этот тест зелёный, самый противный класс багов закрыт.
- **PHPUnit + Brain Monkey** (конвертация габаритов, упаковка отправлений, маппинг статусов и кодов ошибок), интеграционные через wp-env, **Playwright** на сквозной чекаут.
- **Режим dry-run** в настройках: запросы на запись логируются, но не уходят. Нужен и при отсутствии песочницы, и чужим пользователям.
- **Кнопка «Скопировать диагностику»** в админке: версии, настройки без секретов, последние строки лога. Это то, что просишь у пользователя вместо переписки.
- Боевая проверка: staging `test.spokinoki.ru`, первый реальный заказ на себя, минимальная сумма, реальное получение в ПВЗ.

## 6. Публикация

**Каталог WordPress.org — основной канал.** GPLv2+, `readme.txt` по формату, обязательный дисклоуз внешнего сервиса (куда уходят данные, ссылки на условия Ozon), ревью людьми на первой подаче, дальше SVN (`trunk` + `tags`), разработка в Git, релиз скриптом. Слаг не должен начинаться с чужого товарного знака: `ozon-delivery-for-woocommerce` могут развернуть, безопаснее формулировка вида `shipping-integration-for-ozon`. Разрешение на название и логотип имеет смысл получить у Ozon одним письмом вместе с остальными вопросами.

**GitHub + plugin-update-checker** — параллельный канал: автообновления из GitHub Releases, без ревью, удобно для бет.

**Официальный статус у Ozon** — разговор после стабильной версии, когда есть репозиторий, документация и живой магазин на этом плагине.

**CI:** PHPCS (WordPress Coding Standards), PHPStan 6+, PHPUnit, сборка zip без dev-зависимостей и без `docs/*.json` (`.distignore`), автопубликация тега.

**Персональные данные.** Плагин передаёт в Ozon телефон, ФИО и адрес покупателя. Нужны: упоминание Ozon как обработчика в политике конфиденциальности, галка согласия на чекауте, раздел в readme для каталога.

## 7. CLAUDE.md проекта

1. Источник истины — `docs/API.md`, полная схема `docs/ozon-delivery.swagger.json`. Полей не выдумывать: нет в спеке — остановиться и спросить.
2. Все запросы идут через `Api\Transport`, который сам решает OAuth, редиректы `testcookie` и 429. Прямой `wp_remote_post` в бизнес-коде запрещён.
3. HTTP 200 не значит успех: всегда разбирать `results[].error`.
4. `order/create` только с `Idempotency-Key` и `order_external_id`.
5. Ошибки расчёта не выбрасывать через `wc_add_notice('error')`.
6. Каждая точка решения — через `apply_filters('ozon_delivery_…')`.
7. Секреты и токены никогда не попадают в лог в открытом виде.
8. Единицы: Ozon принимает граммы и миллиметры. Конвертация только в `Shipping\Dimensions`.
9. **Тест пишется первым.** Сначала падающий тест, потом код. Функция без теста в коммит не уходит.
10. Структуру ответов Ozon не выдумывать: сначала записать живой ответ в `tests/Fixtures/`, тест писать против фикстуры.
11. Перед коммитом `composer lint` и `composer test`. Красный тест — не повод его удалить или пометить skipped.
